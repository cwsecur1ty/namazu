# Desktop capability and persistence audit

This checklist records the delivered Namazu capabilities and their desktop destinations. “Implemented” means the underlying code and named regression tests exist; it does not mean every workflow was exercised against a real service. “Partial” identifies a remaining distribution limitation. Local fixture checks establish product behavior, not API security coverage.

The earlier Windows artifact passed four automated journey groups: main requests,
multi-contract workspaces, advanced tools and detection. Those historical checks
do not validate the subsequent custom header. See
[header and Bruno validation](desktop-header-bruno-validation.md) for the current
build's fresh checks and limitations, and [previous desktop validation](desktop-validation.md)
for the earlier native inspection. Native-window control remains stopped at the
user's request; headless packaged-resource tests are a separate surface.

## Persistence before this change

The source inspection found audit runs in `~/.namazu/runs.db` with SQLite WAL sidecars and multi-contract workspaces in sibling `workspaces.db`. Workspace bearer profiles kept values only in process memory. The older browser editor kept request history only in JavaScript memory. Its theme, layout, example data, access matrices, sequences and selected settings used origin-specific `localStorage`. A native application cannot read a different browser's profile or recover an ended browser's in-memory history.

An explicit browser-preferences export can carry a reviewed subset into the desktop app. The `namazu-browser-preferences` version-1 envelope accepts only named display preferences and `namazu-examples:` / `namazu-access:` JSON data. JSON is parsed before redaction, preserving safe structure while masking named credential values and echoes of available workspace credentials. Context keys remain separate until the user selects which legacy entry to apply. Importing these values does not execute sequence steps, evaluate scripts, assign identities or acquire tokens.

Desktop state is now kept under `%LOCALAPPDATA%/Namazu` on Windows, unless `NAMAZU_STATE_DIR` selects a different directory. `NAMAZU_DESKTOP=1` selects the desktop layout; the ordinary web CLI retains its previous default paths.

| Directory/file | Contents and format |
|---|---|
| `config/desktop-state.json` | `namazu-desktop-state`, version 1, revision plus sanitized UI state. |
| `config/window-placement.json` | Version-1 native bounds, monitor/DPI, maximised state and theme; no credentials. Monitor/DPI changes are fitted to the available work area. |
| `config/desktop-state.json.bak` | Previous successful state for corruption recovery; credentials are already masked. |
| `config/desktop-state.json.corrupt-*` | Preserved unreadable state, created before recovery; inspect locally before sharing it. |
| `config/migration-v1.json` | `namazu-desktop-migration`, version 1, source/destination/backup paths and snapshot checksums. |
| `workspaces/workspaces.db` | Contract inventories, profiles as references, configurations, reviewed plans and historical snapshots; SQLite schema 1. |
| `evidence/runs.db` | Incremental audit runs, cases and network receipts; SQLite schema 1. |
| `evidence/requests.db` | Ordinary request receipts and results, owned by the desktop request manager; SQLite schema 1. |
| `evidence/oob.db` | Explicit callback cases, context bindings, imported observations and receipt references; SQLite schema 1. |
| `secrets/credentials.json` | `namazu-credentials`, version 1, encrypted DPAPI blobs keyed by opaque references. Session-only secrets never enter this file. |
| `backups/*.migration-*.db` | Verified recoverable snapshots of legacy SQLite databases. Original legacy files remain in place. |
| `cache/`, `logs/` | Separate desktop-owned cache and diagnostic locations; never a place to store plaintext bearer values. |

Legacy database migration uses SQLite's backup API, including committed WAL data. It leaves the source database and its sidecars in place, retains a verified migration backup, and never replaces an existing desktop destination. A corrupt source or failed backup stops migration with an error rather than silently starting an empty replacement. Schema-0 runs/workspaces receive the schema-1 marker without rewriting their retained rows; future versions are refused before modifying them.

State saves compare the submitted revision with the current on-disk revision while holding a process-safe lock. Stale windows receive a conflict instead of overwriting another window. Writes are staged and flushed before atomic replacement; failed writes preserve the prior state. An unreadable state is copied aside, then the last valid backup is restored when available. Recovery itself performs no requests, OAuth exchange or audit resumption.

Windows credential persistence uses [current-user DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata), with the reference bound into encryption context. Decryption and integrity checks use [CryptUnprotectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptunprotectdata). This protects stored values at rest; it does not protect credentials from software already running as that Windows user or from memory inspection during use. Changing back to session-only removes the saved encrypted reference. Workspace exports contain references and assignments only, and importing an export requires fresh credential setup.

## Validation boundary

The earlier desktop suite reported **1,386 passed, one skipped**, with nine
packaged lifecycle checks and four headless journey groups. Those numbers belong
to the historical build documented in [desktop-validation.md](desktop-validation.md).
The current header/Bruno update's source suite passes **1,463 tests, one skipped**.
Its rebuilt backend passes nine lifecycle checks and all six headless journey
groups: main workspace, multi-contract, advanced, detection, Bruno and header.
The Bruno journey preserves an existing contract, draft and explicit identity
assignment through import and restart. Fresh artifact checks and screenshots are recorded in
[desktop-header-bruno-validation.md](desktop-header-bruno-validation.md).
These checks establish local application behavior, not API security coverage,
universal platform compatibility or third-party scanner coverage.

`test_desktop_state.py` covers temporary per-user paths, state round trips, concurrent stale writes, sensitive draft/environment redaction, preserved identity context, corrupt-state recovery, failed writes/disk-full simulation, future-format refusal, legacy WAL migration and backups, explicit session/DPAPI storage, reference binding, credential restart behavior and export/import separation. A Windows-only test exercises the actual DPAPI API with inert fixture data. These checks use local files, local fixtures and mocks. They establish persistence and product boundaries, not security coverage of any API.

`tests/desktop_advanced_ui.py` runs the default desktop frontend against an isolated backend and loopback documentation/API fixture. It exercises missing-business-data guidance, recorded successful controls, explicit two-identity permission planning, successful and mixed historical report imports, offline reassessment, Bruno report/collection conversion, explicit browser preference migration and expert navigation. These are offline journeys: its fixture counter remains at zero endpoint requests. The mixed historical report retains 141 recorded attempts / 135 responses, with application denials, field validation, edge blocks and incomplete attempts separated. Those are imported fixture counts, not requests sent by the check. Screenshots and the machine-readable result are written under `.local-reports/desktop-advanced`; nested narrow-layout measurements are recorded rather than silently treating a clipped panel as a visual pass.

`tests/desktop_detection_ui.py` checks explicit callback preparation, exact draft insertion, write-consent reset, matched/unmatched JSONL events, duplicate accounting, secret redaction, inert response markup, historical evidence roundtrips and the existing native fuzz plan. Source and final packaged headless checks pass at 1440px and 390px with zero target requests, zero external browser requests and no measured horizontal overflow in these views. Source screenshots and results are under `.local-reports/desktop-detection`; `.local-reports/packaged-windows-final` belongs to the earlier build. Current results are under `.local-reports/header-bruno-packaged-main`, `header-bruno-packaged-advanced`, `header-bruno-packaged-bruno` and `header-bruno-packaged-header`. The packaged scripts hold the private loopback session capability only in memory. They do not open or control a native window.
